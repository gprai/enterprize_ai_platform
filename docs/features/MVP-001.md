## Objective

Create a secure, read-only knowledge assistant for the approved Enterprise AI Architecture project documents. The assistant must provide concise answers grounded in retrieved evidence, identify its sources, and abstain rather than invent information when the approved corpus does not contain enough evidence.

The MVP supports personal learning, implementation guidance, architecture interviews, and presentations. It does not authorize production use, cloud deployment, or real-world actions.

## Business problem and outcome

The project architecture, security controls, implementation plan, and technology decisions are distributed across long documents. The owner needs a searchable assistant that makes this material easier to understand without weakening its evidence or authorization boundaries.

The expected outcome is that the owner can ask questions about the architecture, weekly plan, security controls, technology decisions, rollback, and teardown and receive either:

1. an evidence-grounded answer with citations to approved sources; or
2. a safe abstention when sufficient authorized evidence is unavailable.

## Target users and action boundary

- **Primary user:** Gyan Prakash Rai, project owner and engineer.
- **Secondary users:** None for the initial MVP.
- **Excluded users:** Anonymous, public, production, and unapproved users.

For this single-engineer learning project, Gyan Prakash Rai performs the business, data, security, evaluation, technical-owner, and acceptance roles. This learning exception is not equivalent to enterprise segregation of duties and must be reviewed before any production design.

The MVP is read-only. It may retrieve authorized evidence and generate cited answers or abstentions. It must not perform real write actions, mutate infrastructure, approve deployments, or operate as an unrestricted autonomous agent.

## Scope

### In scope

- Read-only questions over approved project documents.
- Authorization-filtered retrieval.
- Answers whose citations refer only to supplied retrieved context.
- Safe abstention when evidence is unavailable or insufficient.
- Local development using Qdrant in a later approved task.
- Provider-neutral model, embedding, and vector-store interfaces in later tasks.
- Synthetic local identity and authorization metadata for MVP tests.

### Out of scope

- Production or client-confidential data.
- Public or anonymous access.
- Real write actions or unrestricted autonomous agents.
- Production deployment approval.
- Multi-region disaster recovery.
- AWS upload, deployment, or resource mutation under this feature.
- Selection of an organization identity provider, AWS account/region, or Bedrock model.

## Measurable acceptance criteria

### Scope acceptance

- All five starter questions have explicit expected facts or an abstention outcome.
- Q1 through Q4 must return the expected facts with citations referencing supplied retrieved context.
- Q5 must abstain without inventing a production date or supporting source.
- A `tenant-a` `reader` must receive zero chunks from the `tenant-b` restricted fixture.
- No plaintext secret, credential, production data, or client-confidential data may be introduced.
- No consequential action is enabled by this MVP.

### Later implementation and evaluation gates

- All five initial cases must behave correctly.
- Recall@5 must be at least 0.85 on the W3-002 25-case golden set.
- All citations must reference supplied retrieved context.
- Grounded-answer or correct-abstention rate must be at least 95%.
- Cross-tenant leakage tolerance is zero.
- Prompt-injection cases must fail safely.
- Local retrieval p99 must be below 750 milliseconds after warm-up.
- End-to-end p95 must be below 4 seconds with the fake or a separately approved provider.
- Initial local paid-platform cost must remain USD 0.

These executable gates are requirements for later tasks. They are **NOT RUN** for this documentation-only task and must not be reported as passed.

Material failure includes unauthorized retrieval, secret exposure, an invalid citation, Recall@5 below 0.85, a Recall@5 reduction greater than 0.05 from the approved baseline, grounded-answer/correct-abstention below 95%, or exceeding an approved paid-platform budget. A failed or unexecuted test must never be reported as passed.

## Privacy and security assumptions

- Only synthetic, sanitized, non-sensitive learning data is approved for the local MVP.
- Authorization is enforced before retrieval using trusted identity and metadata, not model instructions.
- Retrieved text is treated as untrusted input.
- Prompt-injection content cannot override system controls, authorization, or the action boundary.
- Logs and evidence must not contain raw secrets, credentials, unnecessary personal data, or full sensitive documents.
- No data may be uploaded to AWS or another external provider without separate privacy, residency, cost, and mutation approval.
- No plaintext secrets or long-lived AWS credentials are permitted.

## Learning and interview talking points

**Business use case:** make distributed architecture knowledge searchable while retaining evidence, access control, and safe refusal.

**Technical importance:** this scope becomes the source for retrieval tests, evaluation cases, authorization expectations, and release gates. It prevents later implementation from defining success after the fact.

**Layman explanation:** the assistant is an open-book helper. It may answer only from the approved books it is allowed to see, must show which book supports the answer, and must say it does not know when the books do not contain the answer.

Interview-ready points:

- Why a narrow, measurable use case comes before platform implementation.
- Why RAG and citations are preferred for current project knowledge.
- Why authorization is enforced before retrieval rather than in a prompt.
- Why abstention is a successful safety outcome rather than a failure.
- Why five starter cases are useful now while the statistically broader set belongs in Week 3.

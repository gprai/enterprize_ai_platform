## Policy architecture and trust boundary

The gate has two independent policy engines:

- OPA evaluates a strict, supported Terraform plan-shaped contract against the ordered W5 policy inventory. It fails closed when the input contract, evaluation context, exception registry, supported resource type, action sequence, or known-value boundary is invalid.
- Checkov statically scans Terraform source using the repository configuration. Its configuration is offline: policy download, external-module download, and result upload are disabled; soft-fail is disabled.

OPA consumes only plan-shaped input plus an explicit evaluation time and exact policy-ID inventory. The committed exception data is loaded through fixed data leaves. Findings are normalized and sorted before release. Checkov uses built-in Terraform checks plus exact, inline, owner-approved skip directives; no custom Checkov Python policy path is used.

The trust boundary excludes Terraform state, credentials, provider responses, Bedrock prompts and answers, raw exception payloads, stack traces, and unredacted scanner output from this evidence.

## Exception-governance contract

The committed registry is canonical JSON with schema `w5-003.policy-exceptions.v1` and an initially empty `exceptions` array. No Checkov skip is copied into it.

An exception has exactly ten ordered keys: `exception_id`, `policy_id`, `resource_addresses`, `owner`, `approver`, `rationale`, `evidence_reference`, `issued_at`, `expires_at`, and `status`. It must:

- bind one exemptible policy to 1–10 unique, explicit Terraform resource addresses;
- contain no wildcard, glob, directory, source-file, or blanket scope;
- name Gyan Prakash Rai as both owner and approver;
- include bounded rationale and evidence reference text;
- use valid UTC issue and expiry timestamps;
- expire no more than seven days after issue;
- have status `ACTIVE` or `REVOKED`;
- have unique exception IDs and unique policy/resource bindings.

`W5-PLAN-001`, `W5-SEC-001`, and `W5-EXC-001` are non-exemptible. Future, expired, revoked, absent, and invalid exception states remain explicit; only a currently active, valid, exact resource binding can suppress an exemptible finding.

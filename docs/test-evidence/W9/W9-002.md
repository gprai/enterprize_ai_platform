## Business and architecture outcome

The implemented source-only flow is:

`approved experiment identities → active same-tenant authorization → exact policy identity → privacy-safe admission → bounded in-memory run → terminal redacted record → compatible-context metric comparison → disable → verified export → exact owner-controlled purge plan`

The intended future managed flow remains:

`approved experiment inputs → bounded MLflow run → privacy-safe metrics/artifacts → reproducible comparison → retained or torn-down lineage record`

Only the first, process-local flow was implemented and tested. The package has
no MLflow SDK, tracking socket, environment-client discovery, subprocess,
filesystem backend, cloud client, model download, registry, deployment, or
promotion call. Both deployment and promotion remain `NOT_AUTHORIZED`; the
tracking URI remains `OWNER_BINDING_REQUIRED`.

In plain language, this is a lab notebook that records the exact ingredients
and results of an experiment but cannot authorize factory release. A better
score is evidence for review, not permission to deploy.

The business beneficiaries are model developers, reviewers, model risk,
security, privacy, and operations. The value is a reproducible, access-bound
record that allows like-for-like comparison without storing raw prompts,
responses, evidence, secrets, or production data.

Run admission occurs in this order:

1. Require a UTC service time and an active administrator authorization.
2. Match hashed tenant, subject, authorization context, and clearance before
   any store access.
3. Reject secret-like or raw-content parameter and artifact names.
4. Match the run's exact policy identity and dataset classification.
5. Reject expired deadlines.
6. Return the prior result for an identical idempotent replay; reject reuse of
   the same key with different admitted bytes.
7. Enforce one active run globally and one per tenant.
8. Create a bounded in-memory record, terminate it as `COMPLETED`, and retain
   the result identity.
9. On a post-admission failure, attempt to preserve only an `INVALIDATED`
   terminal record with a safe reason code.
10. Release concurrency counters in `finally`.

Comparison separately requires an active reviewer or administrator in the same
tenant with sufficient clearance. Both records must be completed and must have
the same dataset, code, prompt, embedding, retrieval, evaluation-contract,
classification, tenant, metric inventory, and metric units. A model identity
may differ visibly so the reviewer can evaluate a candidate, but comparison
does not change either record and cannot approve promotion or deployment.

## Identity, schema, and privacy controls

The `w9-002.experiment-input.v1` contract binds:

- synthetic non-production dataset version, manifest SHA-256, case-inventory
  SHA-256, case count, and `PUBLIC` or `INTERNAL` classification;
- exact Git commit and source-composition SHA-256;
- prompt version and prompt-template SHA-256 without prompt text;
- model provider, ID, immutable revision, optional artifact SHA-256, license,
  and approval-reference SHA-256;
- immutable 384-dimension normalized cosine embedding identity and artifact
  SHA-256;
- fake, Qdrant, or OpenSearch collection identity, revision, specification
  SHA-256, and retrieval-policy SHA-256;
- W3-002 report/evaluator/metric versions, dataset/configuration/payload
  checksums, gate status, and baseline-comparison status;
- sorted unique redacted parameters, bounded aggregate metrics, and safe
  relative redacted artifact references.

The `w9-002.run-envelope.v1` contract adds canonical run and correlation UUIDs,
an idempotency key, hashed tenant/subject/authorization references,
classification, exact policy SHA-256, UTC request time, and a deadline no more
than 900 seconds later. The `w9-002.run-record.v1` contract records one of
`RUNNING`, `COMPLETED`, `INVALIDATED`, or `CANCELLED`, with terminal records
immutable and deployment/promotion fixed to `NOT_AUTHORIZED`.

Strict Pydantic models are frozen, reject unknown fields, validate defaults,
strip surrounding string whitespace, and use strict validation. Canonical
serialization rejects unsupported objects, non-string object keys, naive or
non-UTC timestamps, and non-finite decimal values. Parameters, metrics, and
artifacts must be sorted and unique. Dataset and evaluation checksums must
match. Ratio/boolean metrics are bounded to zero through one; duration, token,
cost, and count metrics cannot be negative.

No raw golden-set case, question, answer, prompt, response, reasoning, evidence,
credential, token, or secret is an admitted lineage field. Safe artifact
references are relative POSIX paths and reject absolute paths, traversal,
backslashes, and home aliases.

| Comparison runs | 16 | Policy ceiling; current comparison API is pairwise |

| Export before purge | Required | Purge must bind to the latest exact redacted export |

The store must be disabled only after all runs are terminal. Export is permitted
only after disablement. Purge requires the exact sorted run inventory and the
SHA-256 identity of the latest redacted export. A cleanup plan names exact run
IDs and explicitly retains the redacted export and shared resources.

## Security, reliability, and failure behavior

- Cross-tenant, subject, authorization-context, and clearance mismatches fail
  before store access.
- Policy substitution, classification mismatch, expired deadlines, conflicting
  idempotent replay, and concurrency exhaustion fail closed.
- Duplicate YAML keys and YAML aliases are rejected.
- Secret-like and raw-content parameter/artifact names fail before storage.
- Mutable model revisions such as `latest`, `main`, and `master` are rejected.
- Metric inventories and units must match before comparison.
- Terminal records cannot be rewritten; cancellation cannot later become
  completion.
- A failure after record creation preserves an invalidated safe record when
  possible and never implies promotion.
- Disablement blocks new runs while allowing a redacted export.
- Purge is impossible without disablement, exact inventory, and latest-export
  identity binding.
- The source package contains no vendor import, socket, subprocess,
  environment-variable client, runtime/evidence directory, or plaintext
  credential.

The implementation does not establish real MLflow authentication, TLS,
least-privilege service identity, backend availability, distributed locking,
multi-process concurrency, managed retention, data residency enforcement,
backup/restore, observability, service SLOs, production privacy review, or
cloud cleanup. Those remain owner-controlled future design and evidence gates.

## Decision and alternatives

The selected direction separates reproducible experiment evidence from release
authority. It uses provider-neutral immutable records and a process-local
MLflow-compatible store so privacy, comparison, lifecycle, and consumer
contracts can be proven without a vendor dependency or live backend.

The rejected default is to log raw prompts, responses, evidence, credentials,
or production data, or to interpret the highest metric as production approval.
That alternative would mix evaluation with governance, enlarge privacy and
security exposure, and make lineage unable to prove what was actually compared.

A real MLflow backend becomes justified only after owner approval of the
external identities and operational controls listed above. That future choice
must preserve the current domain contracts or explicitly revise them through a
new governed decision; it cannot silently broaden this source-only authority.

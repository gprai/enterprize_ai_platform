## Business and architecture outcome

The implemented source-only flow is:

`exact evaluated package and lineage → active same-tenant authorization → exact registry policy → process-local registration → independent package review → independently approved CANDIDATE-to-STAGING promotion → independently approved STAGING-to-PRODUCTION promotion → explicit known-good identity → exact rollback when required`

The intended future managed flow remains:

`approved immutable package → separately authorized SageMaker registry mutation → environment promotion → separately authorized deployment → monitored operation or exact known-good rollback`

Only the first, process-local flow was implemented and tested. The source can
render reviewable SageMaker-compatible register and approval-update requests,
but every rendered request states `submission_status=NOT_AUTHORIZED` and
`deployment_approval=NOT_AUTHORIZED`. The package contains no AWS SDK, network,
credential, environment-discovery, subprocess, model-download, deployment, or
endpoint call.

In plain language, this is a controlled release vault. A signed,
serial-numbered item can move between separately controlled shelves only after
the correct independent approvals; moving it does not install or run it. If the
current production identity is unsafe, rollback selects the exact previously
recorded known-good serial number while retaining the failed candidate and the
audit trail.

The business beneficiaries are model developers, model risk, security,
operations, release approvers, and auditors. The value is a fail-closed chain
from training and evaluation evidence to a reviewable package, without
allowing mutable tags, self-approval, stage skipping, best-metric automation,
or implicit deployment.

The principal decision sequence is:

1. Require UTC service time and active same-tenant authorization with the
   required role and classification clearance before registry-store access.
2. Bind registration to the exact policy, artifact, object version, container
   digest, code, training request, experiment/evaluation lineage, model card,
   tenant, registrant, authorization context, deadline, and idempotency key.
3. Require a separate reviewer to approve or reject the exact package. A
   registrant cannot approve the registrant's own package.
4. Require a separate promotion approval bound to the exact package approval,
   source stage, adjacent target stage, current target identity, policy,
   executor, tenant, deadline, and idempotency identity.
5. Permit only `CANDIDATE → STAGING → PRODUCTION`; direct candidate-to-
   production promotion and target substitution fail closed.
6. Record a production package as known-good only through a separately
   authorized reviewer identity and exact audit event.
7. Bind rollback to the expected current production package, exact known-good
   reference, target stage, policy, tenant, executor, approval, and deadline.
8. Restore only that known-good production identity, preserve the failed
   candidate and audit evidence, and keep deployment unauthorized.
9. Require registry disablement and a latest exact audit export before an
   owner-approved purge of eligible identities; shared resources remain
   outside the purge boundary.

## Identity, schema, and model-card controls

The `w9-003.model-package-manifest.v1` contract binds:

- package, request, correlation, idempotency, tenant, registrant, and
  authorization references;
- `PUBLIC` or `INTERNAL` classification and `ap-southeast-1` processing region;
- exact versioned S3 model artifact URI, object-version identity, SHA-256, and
  size;
- immutable container registry URI and image digest;
- exact source Git commit and source-composition SHA-256;
- exact W9-001 training-request identity;
- the complete W9-002 experiment input/run lineage, including evaluation,
  dataset, code, prompt, model, embedding, retrieval, and artifact identities;
- model name, immutable version, license, intended-use statements, excluded-use
  statements, risk statements, evaluation report identity, and owner reference;
- exact registry-policy SHA-256; and
- UTC request/deadline values bounded by the policy's 900-second request limit.

Strict Pydantic models are frozen, reject unknown fields, validate defaults,
and use strict runtime validation. Canonical serialization rejects unsupported
objects, non-string object keys, naive or non-UTC timestamps, and non-finite
decimals. Ordered statements and immutable model versions are required. A
package whose artifact, container, code, training request, experiment run,
evaluation payload, model card, policy, or authorization identity differs from
the reviewed bytes is a different package and cannot inherit approval.

## Policy, promotion, audit, and retention limits

| Control | Implemented source value | Evidence meaning |
|---|---:|---|
| Operating mode | `process_local_memory` | Local contract only; not SageMaker Model Registry |
| Active mutations globally | 1 | In-process admission limit, not a distributed quota |
| Active mutations per tenant | 1 | In-process same-tenant concurrency gate |
| Retained packages | 100 | Exact process-local store ceiling |
| Retained audit events | 1,000 | Exact process-local audit ceiling |
| Maximum request time | 900 seconds | Registration/promotion/rollback deadline ceiling |
| Automatic retries | 0 | Unknown external mutation cannot be repeated |
| Stage order | `CANDIDATE`, `STAGING`, `PRODUCTION` | Only adjacent forward promotion is permitted |
| Direct candidate-to-production | `false` | Stage skipping fails closed |
| Separation of duties | Required | Registrant/executor cannot self-approve the governed action |
| Audit export retention | 180 days | Source policy only; no external retention store exists |
| Failed candidates | Preserved | Rollback does not erase the failed package or evidence |
| Shared-resource deletion | Forbidden | Cleanup cannot imply service or platform deletion |
| Model package group | `OWNER_BINDING_REQUIRED` | No real SageMaker group is selected |
| Registry mutation/deployment | `NOT_AUTHORIZED` | Rendering and local state cannot authorize AWS or deployment |
| Network access | `false` | The W9-003 package has no live provider path |

Audit events are canonically fingerprinted and hash-linked. Export binds the
complete ordered event chain and policy identity. Cleanup planning identifies
only eligible retired package IDs, preserves failed candidates and audit
evidence, and reports `NOT_RUN` until an explicit owner-approved purge supplies
the exact export identity and approval reference.

## Security, privacy, reliability, and failure behavior

- Cross-tenant, subject, authorization-context, role, or clearance mismatches
  fail before registry-store access.
- Package review, promotion, known-good marking, and rollback use separate
  reviewer/executor identities; self-approval fails closed.
- Mutable model versions and tags, mutable container identity, unsafe S3
  identity, and nested training/evaluation lineage substitution are rejected.
- Policy substitution, expired or future-dated approvals, deadline expiry,
  non-adjacent stage movement, expected-current mismatch, known-good
  substitution, and conflicting idempotency reuse fail closed.
- Cancellation cannot undo an applied promotion, and a cancelled promotion
  cannot later apply.
- Concurrency counters are released in `finally`; identical completed requests
  replay deterministically while conflicting reuse is rejected.
- Raw model content, prompts, responses, evaluation cases, credentials, and
  provider envelopes are not registry fields or evidence content.
- Audit export precedes exact purge; shared resources and failed candidates are
  retained by policy.
- SageMaker-compatible rendering is not submission. Serving projection is not
  deployment, endpoint approval, or inference authorization.

The implementation does not establish real IAM least privilege, KMS behavior,
private endpoints, package-group policy, SageMaker authentication/TLS,
distributed locking, multi-process concurrency, backup/restore, operational
monitoring, production model-risk review, data residency enforcement, registry
availability/SLOs, live retention deletion, cloud cleanup, or billing
reconciliation. These remain owner-controlled future design and evidence gates.

## Business and architecture outcome

The implemented source-only flow is:

`immutable model/data/code/container/hyperparameters/cache identities → trusted tenant/classification authorization → exact policy identity → independent request-bound approval and budget ceiling → PEFT/cost/resource/capability admission → deterministic SageMaker-compatible request rendering → identity-bound candidate specification`

The intended future live flow remains:

`approved immutable inputs → approval-bound SageMaker training → bounded PyTorch/Hugging Face/PEFT run → evaluation artifact → failed-job cleanup`

Only the first, source-only flow was implemented and tested. The offline
provider cannot submit a job. It returns a reviewable candidate specification
whose `submission_status` and result both state `NOT_AUTHORIZED`.

In plain language, this is a controlled laboratory experiment where every
ingredient, instrument, operator, and budget is logged before starting. W9-001
builds and checks the experiment sheet; it does not turn on the equipment.

The business beneficiaries are model developers, model risk, security, and
FinOps. The value is a repeatable fail-closed decision boundary that prevents
mutable, unlicensed, cross-tenant, secret-bearing, unbudgeted, or oversized
training inputs from becoming an implied job submission.

## Components, producers, consumers, and decision flow

| Component | Responsibility | Producer / consumer boundary |
|---|---|---|

| `models.py` | Strict immutable identities for model, data, code, container, hyperparameters, cache, resources, PEFT, approval, request, result, and cleanup plan | Consumed by the service, provider renderer, orchestration identity handoff, fakes, and tests |
| `serialization.py` | Canonical sorted compact JSON and SHA-256 fingerprints | Binds policy, request, provider request, approval, idempotency, and candidate identities |
| `policy.py` | Duplicate-safe YAML loading and exact W9 limit validation | Rejects aliases, duplicate keys, invalid encoding/size, extra fields, and wrong feature order |
| `capabilities.py` | Injectable CPU/GPU capability detection | Reads only the injected runtime; unavailable or inconsistent GPU evidence fails closed |
| `contracts.py` | Provider-neutral runtime, authorizer, and provider protocols | Keeps cloud SDK objects outside the training contract |
| `service.py` | Ordered authorization, policy, approval, PEFT, resource, idempotency, concurrency, capability, and result-binding gates | Calls the provider only after every earlier gate succeeds and releases capacity in `finally` |
| `sagemaker.py` | Deterministic SageMaker-compatible request renderer and offline provider | Produces a candidate specification only; contains no SDK, network, registry, model-download, or job-submission call |
| W8 orchestration models/engine | Carries a dedicated training-request identity through the shared workflow engine | Model training no longer pretends to be a SageMaker real-time serving route or consume a serving artifact identity |
| Feature matrix/platform validation | Registers `TRAIN-001` and `COST-006`, their exact source paths, and control contracts | Makes source composition and stale-consumer drift fail validation |
| W9 unit/contract/integration/feature/security/rollback/teardown tests | Proves deterministic positive, negative, failure, and residue behavior | Uses synthetic inputs and injected fakes only |

Authorization and admission occur in this order:

1. Require an active trusted administrator authorization context in UTC.
2. Match hashed tenant, subject, authorization context, and classification.
3. Match the request's exact training-policy fingerprint.
4. Match an independent, unexpired approval to the exact request, tenant,
   requester, approval reference, and positive cost ceiling.
5. Require an explicit approval for PEFT/LoRA.
6. Enforce owner-bound instance type and hard instance, runtime, storage,
   concurrency, and retry limits.
7. Return an identical result for an identical idempotent replay; reject a key
   reused with different request bytes.
8. Verify injected CPU/GPU capability.
9. Render the offline provider request and require its result identity to match
   the admitted request.

No provider, registry, storage, model, training, or mutation boundary is reached
before authorization and admission succeed.

## Immutable identities and schema controls

The `w9-001.training-request.v1` contract binds:

- request, correlation, idempotency, tenant, subject, and authorization
  references;
- classification and an exact `ap-southeast-1` data-region value;
- Hugging Face repository, exact 40-character revision, manifest SHA-256,
  license, `trust_remote_code=false`, `local_files_only=true`, and
  `use_safetensors=true`;
- versioned S3 data URI, data manifest, tenant, and classification;
- Git commit and source SHA-256;
- container registry URI and matching immutable image digest;
- sorted unique non-secret hyperparameters;
- sorted unique cache entries with safe relative paths, sizes, and SHA-256
  identities;
- CPU/GPU request, exact one-instance count, runtime, and volume;
- PEFT/LoRA method, rank, and sorted unique target modules;
- exact policy, budget, and approval references; and
- UTC request/deadline timestamps bounded by requested runtime.

Strict Pydantic models are frozen, reject unknown fields, validate defaults,
strip surrounding string whitespace, and use strict validation at runtime
boundaries. Canonical serialization rejects non-finite decimals, naive or
non-UTC timestamps, non-string object keys, unsupported objects, and JSON NaN.

## Security, privacy, reliability, and failure behavior

- Tenant, subject, authorization-context, and classification mismatches fail
  before provider preparation.
- Request, policy, approval, budget, model, data, code, container, cache, and
  provider result identities are digest-bound.
- Mutable image tags and mismatched container digests are rejected.
- Credential-like hyperparameter names are rejected; no plaintext secret is
  permitted in the contract or rendered request.
- Duplicate YAML keys and YAML aliases are rejected.
- Cache paths reject absolute paths, traversal, backslashes, and home aliases;
  individual and aggregate sizes are bounded.
- Network isolation and inter-container encryption are rendered as required.
- Remote model code is forbidden; local-only safe-tensor loading is required by
  the identity contract.
- PEFT fields must be complete, LoRA-only, sorted, unique, safe-named, and
  independently approved.
- Capability failures, policy substitution, post-approval input substitution,
  expired/invalid approval, concurrency exhaustion, and mismatched provider
  results fail closed.
- Capacity counters are released in `finally`; completed identical requests are
  idempotent and conflicting replays are rejected.

The implementation does not validate real IAM least privilege, bucket policy,
KMS behavior, private endpoints, security groups, data residency, license legal
acceptance, real training data privacy, logs, metrics, model quality, or cloud
cleanup. Those remain owner-controlled future evidence gates.

## Decision and alternatives

The selected direction is owner-managed training only after immutable inputs,
independent approval, capability, resource, security, and cost gates pass.
PEFT/LoRA remains disabled by default and conditional on exact approval.

Rejected defaults are arbitrary remote code, mutable model/data/container
inputs, standing credentials, plaintext secrets, uncontrolled retry,
cross-tenant admission, unapproved GPU spending, and representing an offline
candidate as a trained or approved model.

Reconsideration requires measured business value plus separately approved
identity, residency, security, operational, lifecycle, and cost evidence. A
serving decision remains separate under ADR-019; a training result cannot
silently become deployment authority.

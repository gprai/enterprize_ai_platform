## Business and architecture outcome

W9-004 extends the existing CI/CD design with a fail-closed model
supply-chain admission contract. A candidate is eligible only when its exact
model artifact, container image, source revision, evaluation result, training
request, experiment run, SBOMs, scanner reports, license evidence, provenance,
policy decision, tenant reference, and data classification agree. The output
is an immutable eligibility record for downstream registry admission; it is
not deployment approval.

The approved decision flow is:

1. A producer identifies one exact, versioned model artifact and its digest.
2. Archive inspection rejects unsafe paths, links, duplicate names,
   disallowed executable/serialized formats, excessive entry counts, or size
   limits before eligibility can pass.
3. Source and Apache-2.0 license evidence, two SBOM formats, four ordered
   scanner records, signed provenance, and evaluation/training/experiment
   identities bind to the same candidate.
4. Critical findings block. High findings require current, candidate-bound
   owner risk treatment. Trivy and Grype disagreement blocks.
5. OPA evaluates the exact input and policy identities. Failed or
   indeterminate evidence cannot be silently converted into PASS.
6. The registry consumer rechecks freshness, all supplied identities,
   classification, policy decision, scanner agreement, and risk treatment.
7. A manually dispatched GitHub workflow may fetch one exact versioned S3
   eligibility record with short-lived read-only OIDC credentials and evaluate
   the local schema and OPA policy. It cannot deploy or promote the model.

| Component | Producer inputs | Output or consumer | Enforced boundary |

The workflow requests only `contents: read` and `id-token: write`. Repository
permissions default to none. The AWS role is supplied through the
`W9_004_READ_ROLE_ARN` repository/environment variable, not a static access
key. The downloaded record lives under the runner temporary directory, is
uploaded as seven-day transient evidence, and is removed in an `always()`
cleanup step. The workflow is inert until the owner supplies the external
bindings and explicitly dispatches it from an eligible repository state.

## Identity, schema, and admissibility controls

The candidate identity binds all of the following:

- credential-free versioned S3 object URI, object version, artifact SHA-256,
  and artifact byte size;
- immutable OCI container digest and container-eligibility digest;
- source repository, 40-character source revision, source-manifest digest,
  Apache-2.0 SPDX identifier, and license-text digest;
- evaluation report, reproducible configuration, training request, and
  experiment run digests;
- tenant reference, `PUBLIC` or `INTERNAL` classification, and
  `ap-southeast-1` region;
- exactly four ordered scanner records: Checkov, Grype, model-format, and
  Trivy;
- exactly two ordered SBOM records: CycloneDX JSON and SPDX JSON;
- provenance statement, signature, issuer, subject, Cosign version,
  verification time, expiry, and evidence status;
- OPA policy/input/decision digests, allow result, ordered reasons, and the
  final eligibility status.

All modeled evidence is immutable and rejects unknown fields. Paths, reasons,
findings, treatments, scanners, and SBOMs must be sorted and unique where the
contract requires deterministic order. Timestamps must be UTC. Eligibility is
fresh for no more than 24 hours, and provenance must still be valid at registry
admission time. `deployment_approval` is fixed to `NOT_AUTHORIZED`.

Result semantics are preserved:

- **PASS**: every mandatory item passes, all exact identities agree, scanners
  agree, OPA allows, critical findings are zero, and each high finding has
  current owner-approved treatment for this candidate.
- **FAIL**: any determinate policy, evidence, identity, scanner, license,
  archive, provenance, or treatment failure blocks the candidate.
- **INDETERMINATE**: evidence cannot establish eligibility. It is not PASS and
  cannot authorize registry admission.
- **NOT_SUPPORTED**: an individual unsupported evidence source contributes to
  an indeterminate candidate unless another determinate failure applies.

## Security, privacy, reliability, and failure behavior

- Secrets and credentials are not schema fields. S3 URIs must not contain
  embedded credentials, query strings, or fragments.
- The tenant is represented by a SHA-256 reference rather than raw tenant
  content. Evidence contains identity and aggregate security facts, not model
  weights, prompts, production records, or private dataset content.
- Hosted-runner handling of a raw candidate is limited to `PUBLIC`; an
  `INTERNAL` candidate may still be represented by its evidence, but raw
  artifact processing requires a separately approved compatible runner.
- Unsafe archive members, serialized executable formats, excess size, stale or
  future-dated evidence, incomplete scanner/SBOM sets, invalid provenance,
  unsupported license, critical findings, untreated high findings, scanner
  disagreement, OPA denial, or any downstream identity mismatch fail closed.
- A failure blocks only the candidate. It preserves the failed candidate and
  canonical vulnerability/provenance evidence for diagnosis and audit.
- Rollback means blocking the candidate and restoring an exact known-good
  package/image through the existing W9-003 contract. W9-004 neither performs
  a registry mutation nor deploys, rolls back, or deletes shared resources.
- Reproducibility comes from immutable identities, deterministic serialization,
  pinned action/tool identities, exact S3 object version and digest, explicit
  policy identity, and preserved decision evidence.

## Decision and alternatives

**Decision:** extend the existing CI/CD approach with a model-specific,
evidence-first gate. Use immutable identities, short-lived OIDC, complete
scanner/SBOM/license/provenance evidence, OPA policy, required reviewers, and
an explicit registry consumer guard. Keep deployment outside W9-004.

**Rejected alternatives:** static cloud credentials; mutable tags or object

unlicensed or unsafe serialized weights; treating INDETERMINATE as PASS;
automatic risk acceptance; automatic production promotion; deleting failed
candidates or their evidence; and claiming live readiness from source-only
tests.

## Learning handover

The owner should be able to explain that software CI/CD proves code quality,
while a model supply-chain gate must also prove the exact model bits, training
and evaluation lineage, license, SBOM, vulnerabilities, signature/provenance,
policy, reviewer decision, and the binding to the registry candidate. A digest
answers “which bytes”; provenance answers “who/what produced them”; OPA and
review answer “whether current policy permits this candidate.” None alone is
deployment approval.

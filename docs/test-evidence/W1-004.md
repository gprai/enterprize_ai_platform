## Business use case

W1-004 establishes a controlled way for the owner to manage an enterprise AI platform throughout its lifecycle: prepare it, inspect a plan, deploy it, validate it, roll it back, destroy it, and check for residual resources. The business objective is to prevent an accidental or unauthorized infrastructure change while preserving a clear approval and recovery trail.

The `platformctl` command-line interface is positioned between the owner and infrastructure tools such as Terraform and AWS. It acts as a policy-enforcing control layer: read-only actions can explain intent, while mutating actions require explicit environment details, immutable inputs, confirmation, and an owner approval record.

## Plain-language explanation

The lifecycle tool is like a locked operations console. Looking at the checklist is allowed, but pressing a button that could create or remove resources requires the correct destination, an approved plan, a confirmation phrase, and proof of authorization. If the tool cannot inspect AWS, it says “I cannot prove it is clean” instead of guessing.

## Implemented and tested architecture position

- `tools/platformctl` provides the lifecycle command surface and approval contracts.
- Provider-free, resource-free Terraform roots establish the approved bootstrap and sandbox structure without defining a deployable cloud workload.
- Fake AWS inventory providers test resource classification and residual detection without making AWS calls.
- `verify-clean` uses a non-zero, fail-closed result when cloud inventory is unavailable. **Fail-closed** means uncertainty is treated as unsafe rather than silently accepted.
- Automated unit, integration, contract, feature, smoke, security, and teardown tests cover the local behavior.

## Key decisions and trade-offs

- **Dry-run and validation first:** reduces accidental change risk but does not prove that a real deployment would succeed.
- **Explicit environment and target:** adds operator effort but makes intent reviewable and less ambiguous.
- **Provider-free Terraform skeleton:** establishes repository structure without credentials or cloud cost, but cannot validate provider behavior or real resources.
- **Mocked AWS inventory:** gives deterministic, cost-free tests but cannot establish live AWS cleanliness.
- **Fail-closed exit code `3`:** prevents an unknown cloud state from being mistaken for success, while requiring later approved live verification if that assurance becomes necessary.
- **Exact lifecycle-aware teardown expectations:** allow only the approved baseline and continue to reject unexpected Terraform, evidence, cache, state, key, and plan artifacts.

## Interview talking points

1. **Why place `platformctl` in front of Terraform and AWS?**  
   It centralizes approval gates, immutable input checks, environment selection, dry-run behavior, and audit-friendly outcomes before infrastructure tools are reached.

2. **What does fail-closed verification mean?**  
   If the system lacks enough evidence to prove cleanliness, it returns an indeterminate non-zero result instead of claiming success.

3. **Why use fake AWS providers in tests?**  
   They make resource and residual classification deterministic, fast, private, and cost-free while keeping live AWS access explicitly opt-in.

4. **What is the difference between rollback and teardown?**  
   Rollback restores a prior known-good release; teardown removes task-owned resources and checks for residue. Neither occurred live in W1-004 because nothing was deployed.

5. **What did the remediation demonstrate?**  
   Repository controls must evolve with approved lifecycle stages. Historical tests were retained but updated to recognize the exact new baseline, then verified with focused and complete regression suites.

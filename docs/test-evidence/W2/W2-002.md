## Business use case

W2-002 gives the platform a controlled way to turn text into numeric vectors for semantic retrieval. A vector represents meaning rather than exact wording, so later ingestion and retrieval tasks can find relevant content even when a query uses different words.

The business value is repeatability and containment. Ordinary automated tests use a deterministic fake provider, while the real public model is tested only through an owner-controlled, offline integration path. This keeps routine development fast and prevents an unexpected model download, network call, GPU selection, or processing of enterprise content.

## Architecture position

The embedding provider sits between text-bearing application workflows and vector retrieval infrastructure. It supplies normalized 384-dimensional vectors compatible with cosine similarity. W2-002 does not create a vector collection, ingest documents, query Qdrant or OpenSearch, or deploy a service.

Two implementations serve different assurance needs:

- `FakeEmbeddingProvider` supplies deterministic vectors for unit, contract, feature and security tests without importing or loading Sentence Transformers.
- `SentenceTransformerEmbedder` loads the explicitly verified local snapshot for the one owner-controlled integration test.

The approved feature remains `RAG-001`, and tracker step `W2-05` is a linked implementation step rather than a separate feature.

## Approved model and runtime contract

- Model: `sentence-transformers/all-MiniLM-L6-v2`
- Immutable revision: `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`
- Output dimension: `384`
- Normalization: enabled
- Compatible similarity metric: cosine
- Device: CPU only; GPU and automatic device selection disabled
- Default batch size: `32`
- Maximum batch size: `128`
- Maximum items per call: `1,024`
- Maximum input: `256` model wordpieces
- Overlength behavior: reject explicitly; never silently truncate
- Runtime model source: explicit external snapshot path only
- Runtime network access: disabled
- Authentication token: none
- Remote code: prohibited
- CPU encode concurrency: one active process-wide operation

Synchronous model work is moved outside the asynchronous event loop. A process-wide lock is acquired inside the worker thread, so cancelling the awaiting coroutine does not permit a second encode operation to overlap the still-running CPU work.

## Failure, rollback and teardown story

Model, revision, path, dimension, normalization or metric mismatches fail before downstream vector query or mutation. Oversized batches, more than 1,024 items and inputs above 256 wordpieces are rejected rather than silently changed. Error and metric paths must not include input text.

## Layman explanation

Routine tests use a predictable stand-in for the AI model. The owner separately downloaded one exact, fingerprinted copy of the real model and then disconnected it from the internet before testing it. The platform checked that every result had the expected shape and that only one CPU job could use the model at a time. The model copy stays outside the source-code folder so it cannot accidentally become part of the repository.

## Decisions and trade-offs

- CPU-only execution is slower than GPU inference but improves portability and avoids unapproved device selection.
- Rejecting long input avoids hidden semantic changes but requires callers to chunk text deliberately.
- A process-wide lock limits throughput but provides predictable CPU use and cancellation safety.
- Deterministic fakes make ordinary tests fast and private, while a separate opt-in test proves compatibility with the real model.
- Pinning a revision and verifying Safetensors reduces supply-chain ambiguity, but does not replace a vulnerability scan or full dependency lock.
- Retaining the cache avoids a repeated download for W2-06 and W2-07, at the cost of intentional external disk residue until teardown.

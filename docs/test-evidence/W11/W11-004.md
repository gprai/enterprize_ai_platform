W11-004 provides a versioned incident workflow in which the exact command,
captured output, exit code, runner version, duration and native verification
must support the result classification. In plain language, it is an aircraft
checklist and flight recorder that cannot label an aborted procedure
successful. The final local results prove deterministic contracts and
fail-closed behavior; they do not prove a live incident response, production
recovery, alert delivery or operational readiness.

## Architecture and producer-consumer flow

```text
versioned incident policy and pinned source identities
  -> severity, role, communication and approval preflight
  -> exact argv plus deadline and approved runner profile
  -> captured stdout/stderr, exit, version, duration and progress
  -> native identity, integrity, health and residue verification
  -> exact SUCCESS / FAILURE / TIMEOUT / NOT_FOUND classification
  -> runbook stage and approved RECOVERY or ROLLBACK action
  -> resume from retained journal without re-running completed commands
  -> cleanup with retained immutable evidence and zero unexpected residue
  -> reviewed game-day evidence and corrective-action gate

live incident, provider operation or production game day -> NOT RUN
```

- `configs/incidents/incident-operations.yaml` is schema
  `w11-004.incident-operations.v1`, environment `sandbox`, classification
  `source-contract-not-live-evidence`, tenant boundary
  `NO_TENANT_DATA_LOCAL_FAKE` and privacy boundary `NO_USER_CONTENT`.
- The runner profiles are Windows PowerShell 5.1 and PowerShell 7. Their
  wrappers consume the shared versioned module and preserve an exact argv
  array instead of rebuilding a shell command string.
- The incident roles are incident commander, operations lead, developer lead,
  security/privacy lead, communications lead, evidence custodian and business
  owner. SEV1, SEV2 and SEV3 define acknowledgement and escalation deadlines.
  Missing acknowledgement blocks progress.
- Allowed communications are owner-approved incident/status records; personal
  destinations are prohibited. The policy contains no personal address.
- The runbook identity is
  `sha256:9e8aae9a6c6cc5364925cfdbca5183b9cb578b987b9698b467559d17bbf140fc`
  for version `incident-runbook-v1`. Its ordered stages are DECLARE, DIAGNOSE,
  CONTAIN, REMEDIATE, ROLLBACK, RECOVERY, NATIVE_VERIFY, CLEANUP and REVIEW.
- CAPACITY and SATURATION require RECOVERY. DEPENDENCY_FAILURE requires
  ROLLBACK. Mutating work is limited to one concurrent action, with zero
  mutation retries. Commands have a 300-second deadline and scenarios a
  900-second deadline.
- `src/enterprise_ai_platform/incident_operations.py` owns strict policy,
  request, journal, evidence, resume, cleanup and classification contracts.
  The local game-day port is injected; it has no live provider or network
  execution path.
- `tools/incidentctl.py` exposes validation, local rehearsal, resume, cleanup
  and cleanliness verification. Evidence is written only to the explicitly
  supplied external root.
- `feature-matrix.yaml` binds the work to blocked features `INC-001` and
  `RUNNER-001`. Platform, feature-matrix and source-composition consumers bind
  the implementation identities so stale protected bytes fail validation.

A nonzero exit, timeout, cancellation, unexpected NotFound, identity or
integrity mismatch, missing native evidence, cleanup failure, incomplete
corrective action or deadline excess cannot become PASS. Expected absence is
accepted only when the request explicitly requires it and native verification
proves that exact absence.

## Security, privacy, reliability and cost

The runners redact credential-shaped captured output, preserve exact argv
arrays and restrict execution to approved policy commands and profiles. The
policy permits no personal communication destination and records no user
content or tenant data. Least privilege still depends on the separately
approved live execution identity; no live credential or role was exercised.

Reliability is fail-closed: a command cannot pass from a zero-looking message
alone, expected absence must be exact, deadlines remain visible, completed
steps are not re-run during resume, failed evidence is retained, and cleanup
requires native absence plus zero unexpected residue. Corrective actions need
an owner and due date and block PASS while incomplete.

No AWS, provider, model, network, Docker, service, deployment or paid cloud
operation ran. Local CPU, storage, electricity and owner time were used but
not monetized. No zero-cost or delayed-billing claim is made.

## Failure, recovery, rollback, teardown and residue

Failure, timeout, cancellation, NotFound, partial action and missing native
verification remain distinct classifications. Resume reads the retained
journal and re-enters at the first incomplete approved step. CAPACITY and
SATURATION terminate in RECOVERY; DEPENDENCY_FAILURE terminates in ROLLBACK.

The bounded rollback, resume, cleanup and teardown tests passed, and all three
game-day records were retained with no unexpected runtime residue. Disabling a
defective runner/playbook and returning to the last validated runbook remains
the approved source-level rollback approach. No live application,
infrastructure, Kubernetes, service, cloud or production rollback/teardown
ran; those activities remain **NOT RUN**.

## Decision and rejected alternative

The decision is to make command execution failure-proof and incident
operations accountable before claiming readiness. The rejected alternative
is ad-hoc shell orchestration that can report PASS after command failure,
discard progress, hide a timeout or leave remediation untracked. The chosen
approach adds evidence and review work but prevents false success.

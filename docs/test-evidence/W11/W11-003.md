W11-003 defines how a recovery candidate must be bound to immutable source,
state and artifact identities before it can be accepted. In plain language, it
is like rebuilding a library from a verified archive while checking every
catalog entry, access record and shelf before reopening it. The local PASS
proves deterministic contracts and fail-closed decisions. It does not prove
that AWS data was backed up, a service was restored, traffic failed over, a
Region was lost, or the approved RPO/RTO was achieved in a live environment.

## Architecture and producer-consumer flow

```text
immutable governed source/state/artifact identities
  -> strict W11 recovery policy and pinned upstream source identities
  -> approved plan for one distinct operation and one recovery scope
  -> tenant, classification, role and deadline preflight
  -> isolated memory-only recovery candidate
  -> exact candidate-identity comparison
  -> ordered native verification:
       identity -> integrity -> authorization -> health -> residue
  -> isolated candidate cleanup
  -> RPO, RTO, identity, authorization, native and cleanup gates
  -> PASS / FAIL / NOT RUN / INDETERMINATE evidence

separately approved live or multi-Region recovery -> NOT RUN
```

  Terraform lineage/serial, an S3 or model object version, an OpenSearch
  collection specification, or a model-registry export identity. Optional
  DNS/ingress identity remains explicit rather than inferred.
- A recovery plan is source-only, carries an approval-reference hash and
  policy hash, and starts as `NOT RUN`. Restore requires an isolated target;
  index rebuild requires the OpenSearch scope and a distinct candidate.
- Authorization requires an active context, the admin role, the same tenant
  and sufficient classification clearance. Public and internal are the only
  approved recovery classifications; a wrong account, Region, tenant,
  classification, role, state lineage/serial, KMS/IAM/routing identity or
  source identity fails closed.

The local result can be PASS only when RPO, RTO, candidate identity,
authorization, all five native verification kinds and cleanup pass. Missing
or incomplete native evidence is `INDETERMINATE`; an explicit failure remains
FAIL. Cancellation, deadline excess, execution uncertainty and cleanup failure
produce safe reason codes and cannot be promoted to recovery success.

## Security, privacy, reliability and cost

The contract is strict, immutable, extra-forbidden and source-only. It records
only bounded identities and safe reason codes; no credentials, tenant content,
prompts, model responses or restored payloads are evidence fields. Recovery
authorization is checked before candidate execution, and the candidate must
remain in the primary account/Region, same tenant and same classification.
Native verification covers identity, integrity, authorization, health and
residue in a fixed order.

The policy pins S3/OpenSearch/model/registry/Terraform, KMS, IAM and relevant
source identities. An identity, state, authorization, scope, deadline,
cancellation or verification mismatch blocks recovery acceptance. A partial
restore is failed or indeterminate; it cannot become PASS merely because a
candidate exists.

No AWS, provider, model, network, Terraform apply, paid service or live data
operation ran for W11-003. Local CPU, storage, electricity and owner time were
used but not monetized. There is no zero-cost claim and no delayed cloud
billing evidence. A future live recovery needs separate authority, exact
accounts/Regions/resources, approved data handling, least privilege, KMS/IAM
and DNS identities, bounded cost, real native verification and a fresh
rollback/teardown plan.

## Failure, rollback, restore, teardown and residue

Backup, restore, index rebuild, rollback and teardown are separate operations
and separate evidence claims. Application rollback is not disaster recovery,
and the presence of a backup or plan is not proof of recoverability.

The local rehearsal creates only an injected in-memory candidate. It aborts
acceptance on identity or scope mismatch, preserves the original source
identity, and cleans the isolated candidate in a `finally`-style path.
Cleanup failure keeps the cleanup gate failed; missing native evidence remains
indeterminate. Automated rollback and teardown tests passed for this bounded
memory-only behavior, and task-specific temporary residue reached zero.

No operational backup, restore, index rebuild, application rollback,
infrastructure rollback, DNS failover, regional failover or cloud teardown ran.
No cloud resource was created or changed by TEST-001, so native cloud residue
and delayed cost verification remain **NOT RUN**. Live RPO/RTO achievement is
also **NOT RUN**, and multi-Region readiness remains **NOT_ESTABLISHED**.

## Decision and rejected alternative

The decision is to treat backup, restore, index rebuild, rollback, teardown and
multi-Region disaster recovery as separate evidence-bound capabilities. The
rejected alternative is claiming disaster recovery from backup configuration,
plans, local fakes, source contracts or an application rollback. This costs
more evidence and operational rehearsal, but prevents a paper plan from being
misrepresented as recoverability.

## Business and architecture outcome

The approved flow remains one service boundary:

`ingress → existing FastAPI authentication/tenant authorization → strict bounded request → rate/concurrency/circuit/drain controls → existing RAG dependency → normalized response or safe error → content-free telemetry`

This is analogous to reinforcing an existing service counter with identity
checks, queue limits, capacity signs, and a controlled closing procedure. It
does not open a second counter with different security rules.

The implemented choice hardens the existing API. The rejected alternatives
were a duplicate inference API, raw provider-specific responses, streaming
without an approved contract, an API-level retry layer that could multiply
downstream attempts, and silent fallback to another provider or local fake.

## Runtime contracts

| Control | Implemented contract |
|---|---|
| Request | Strict `QueryRequest`; query length 1–10,000 characters; existing maximum request body 131,072 bytes |
| Response | Existing normalized, non-streaming API response; provider envelopes remain internal |
| Deadline | API request deadline 25 seconds; Bedrock connect/read values remain 3/20 seconds |
| Retry ownership | API retries `0`; Bedrock SDK total attempts `1`, preventing layered retry amplification |
| Concurrency/backpressure | Maximum four in-flight calls; queue capacity `0`; excess work fails fast |
| Tenant rate | Process-local fixed window: 60 requests per 60 seconds; at most 1,024 tenant digests; raw tenant IDs are not retained |
| RAG circuit | Aggregate process-local circuit: five failures, open 30 seconds, one half-open probe |
| Readiness | Withdrawn while draining or while the RAG circuit is open |
| Client disconnect | Cancels only the scoped in-flight dependency operation under the same deadline |
| Public failures | Stable `api_rate_limited`, `api_draining`, and `rag_circuit_open`; query length preserves `guardrail_input_invalid` |
| Streaming | Disabled; no partial-response lifecycle or audit ambiguity introduced |

Authentication and tenant authorization occur before dependency calls. Rate,
capacity, circuit, and drain decisions do not bypass that trust boundary. The
process-local tenant rate control is not represented as a global ingress quota;
a multi-replica deployment still needs an approved global policy if one is
required.

## Graceful shutdown and lifecycle state

The shutdown sequence is explicit and bounded:

1. Kubernetes `preStop` calls the loopback-only
   `POST /_internal/drain` endpoint. The endpoint is omitted from OpenAPI and
   rejects non-loopback callers.
2. The drain controller immediately marks the process as draining. Readiness
   becomes false, and new query/agent work receives `api_draining` rather than
   entering the dependency path.
3. Registered in-flight work receives up to 20 seconds to finish.
4. Remaining registered work is cancelled with a further two-second bound.
5. Application shutdown closes configured dependencies with a two-second
   bound.
6. The `preStop` call itself has a 23-second timeout inside the existing
   30-second termination grace period.

Tests cover readiness withdrawal, new-work rejection, completed and cancelled
in-flight counts, loopback authorization, cancellation, dependency closure,
and manifest/validator composition. No pod was deployed or terminated, so
actual kubelet timing, load-balancer propagation, multi-replica draining, and
live dependency cancellation remain **NOT RUN**.

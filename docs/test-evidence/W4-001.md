## Business purpose

W4-001 adds an opt-in HTTP boundary around the existing enterprise AI query
flow. It gives callers a small, predictable interface while preserving the
approved health-only application as the default. The boundary validates
untrusted transport data, separates authentication from request content,
delegates authorized queries to the existing RAG service and returns only safe
normalized results or errors.

The owner-executed evidence proves deterministic local behavior using injected
fakes and existing local contracts. It does not prove a live service, live
identity system, provider/model behavior, production performance, deployment
or cloud readiness.

## Implemented scope

### W4-01 — API boundary

- `api_routes_enabled=false` preserves the existing default application
  behavior and the exact legacy `GET /health` response body.
- Enabling the boundary adds `GET /health/live`, `GET /health/ready`,
  `POST /v1/query` and the intentionally disabled `POST /v1/agent`.
- Interactive documentation, OpenAPI and slash redirects are disabled while
  the W4 routes are enabled.
- `/health/live` performs no dependency call. `/health/ready` calls exactly one
  injected local wiring probe under the approved one-second timeout and
  performs no network or cloud probe.
- `/v1/query` accepts only `application/json`, counts the raw body before full
  parsing, enforces the 131,072-byte boundary, rejects malformed, duplicate,
  non-finite and invalid-UTF-8 JSON, and accepts only `query: str`.
- The existing logical RAG guardrail continues to enforce the 10,000-character
  query limit with the existing safe code.
- Responses reuse the trusted citation, usage, prompt-version and abstention
  contracts without exposing prompts, evidence, provider envelopes, internal
  objects or reasoning content.
- Every W4-enabled response receives a new server-generated UUIDv4 in the
  response body and `X-Request-ID` header. Inbound request, correlation and
  forwarded headers are not trusted as that identifier.
- The query boundary uses an application-scoped non-waiting capacity limit of
  four, has no API queue or retry, returns the approved overload response and
  releases capacity after success, error, timeout or cancellation.
- `POST /v1/agent` returns `501 agent_disabled` and resolves no authenticator,
  RAG, retrieval, provider, graph, approval-store or tool dependency.

### W4-02 — Authentication and authorization boundary

- Authentication is an injected asynchronous interface that returns the
  existing trusted `AuthContext` model.
- The default producer fails closed with `503
  authentication_not_configured`.
- Missing, invalid and explicitly denied authentication uses the approved
  `401`, `401` and `403` safe mappings.
- Transport validation occurs before authentication, and authorization denial
  occurs before RAG, retrieval, provider or tool work.
- Request JSON cannot create or override tenant, subject, role, group,
  clearance, issuer, audience, expiry or trusted request identity.
- Existing downstream tenant, clearance, role, group and ACL enforcement is
  preserved. An authenticated caller with no authorized evidence receives the
  existing HTTP 200 `no_authorized_evidence` abstention.
- Live JWT, JWKS, identity-provider, API-key and session integration is not
  part of W4-001.

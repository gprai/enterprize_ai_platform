# W2-001 — Local Retrieval Evidence

## Business use case

W2-001 provides a controlled retrieval foundation for an enterprise AI application. It allows an authorized user to retrieve relevant document chunks without allowing one tenant's data, a more sensitive classification, or an unauthorized role or group to leak into the result set.

The feature supports local learning and contract verification. It does not establish that a production vector service has been deployed or that live business data is ready for use.

## Architecture position

The retrieval layer sits between application or orchestration code and a vector store. A **vector store** keeps document embeddings—numeric representations used to find semantically similar content—together with the metadata required for authorization and traceability.

W2-001 uses one retrieval contract with three adapter positions:

- A deterministic fake provides fast, repeatable offline tests.
- Qdrant provides the owner-executed local integration boundary.
- OpenSearch provides an injected adapter boundary; a live AWS/OpenSearch connection was not exercised.

Qdrant has no host-port publication. The approved one-shot test runner reaches it only through the Compose logical network `qdrant_internal`, whose definition is internal-only. The runtime network name remains project-scoped and is generated by Docker Compose.

## Owner-approved decisions and trade-offs

- The approved DATA-002, DATA-003, EMB-001, and SEC-001 contracts are authoritative for this task.
- Deterministic chunk identifiers preserve stable identity across repeated processing of the same approved identity inputs.
- Retrieval records carry tenant, document, classification, authorization, ownership, content-integrity, PII, ingestion, text, and embedding information required by the approved contracts.
- Authorization is enforced using tenant identity, classification clearance, roles, groups, and operation-specific permissions.
- Qdrant remains internal-only. This prevents convenient host-side HTTP testing, so an additional one-shot runner image is required inside the same internal network.
- The runner uses an immutable Python image index, an explicit Linux/AMD64 constraint, a non-root identity, a read-only filesystem, dropped capabilities, `no-new-privileges`, resource limits, temporary `/tmp`, and no credentials, host ports, Docker socket, host networking, or persistent runner storage.
- Dependency families use repository-approved bounds rather than a complete transitive lock. The build therefore resolved the versions available within those bounds at build time.

## Remediation history

The following failures are retained because they explain why the final architecture and code differ from the first attempt:

1. **FAIL — host-side Qdrant health request.** Qdrant was healthy inside its container, but Docker reported no effective published endpoint for a port attached only to an internal network. The owner selected the internal one-shot runner design. The final architecture removed host-port publication entirely.
2. **FAIL — missing local test dependencies.** The system Python did not contain pytest or the required development packages. The owner created the reusable external environment `E:\AI\.venvs\enterprise_ai_platform`, installed the approved development requirements, and confirmed `pip check` passed.
3. **FAIL — three legacy validator-consumer tests.** They still required a Week 1-only feature matrix after owner-approved RAG-001 was added. A separately approved bounded remediation aligned the validator and consumers; 19 focused tests and the complete suite later passed.
4. **FAIL — four Ruff findings.** Three `timezone.utc` usages and one long assertion were remediated mechanically under a bounded approval. Ruff and the affected tests later passed.
5. **FAIL — one strict MyPy inference finding.** The default-captured OpenSearch lambda was replaced under a one-path approval by an explicitly typed zero-argument `functools.partial`. MyPy later passed with no issues in 25 source files.
6. **Warning remediation.** The first runner build resolved an unpinned external Dockerfile frontend, installed with root pip outside a virtual environment, and used a UID outside the image's normal range. The approved rebuild removed those three conditions.

No failed result above is represented as an initial PASS; each has a later, owner-supplied passing result.

## Access, cost, and privacy

The final runtime test used local Docker CPU, memory, disk, and an internal Docker network. Image and Python dependency resolution used registry and package-index network access and local bandwidth. No owner transcript showed AWS credentials, paid API calls, or a cloud resource deployment.

The integration test used synthetic content. Qdrant was unreachable through a host port, and the runner received no credentials or host resources. These controls reduce exposure, but local success does not establish production privacy, residency, retention, backup, or compliance controls.

## Failure, rollback, and teardown story

The operational failure boundary is fail-closed: if the internal service is unhealthy, the runner cannot proceed; if authorization conditions are not met, retrieval is denied; and if the integration scenario exits through success or failure, its `finally` block attempts collection deletion and verifies absence.

Local teardown was **PASS** and removed the task container, data volume, internal network, and local runner image. Application/source rollback was **NOT RUN**. Any future rollback that changes repository code or configuration requires a new owner approval. Shared base-image caches and the external virtual environment are residual local resources by design.

## Layman explanation

Think of the vector store as a searchable filing room. Each page is stored with a numeric similarity fingerprint and a security label. The retrieval layer checks who is asking, which organization they belong to, what sensitivity they may see, and whether their role or group is allowed before returning a page. The local Qdrant filing room had no door from the host computer; the approved test worker entered through a private internal corridor, performed a synthetic test, removed its temporary drawer, and then disappeared.

- Why a healthy container does not prove that a host port is reachable.
- Why an internal-only network required an in-network test runner.
- How immutable image digests, non-root execution, capability dropping, read-only filesystems, and resource limits reduce supply-chain and runtime risk.
- Why a local Qdrant PASS does not prove live OpenSearch, AWS, deployment, or production readiness.
